# 让 AI 工作一整夜，难点不在“快”而在“别跑偏”

> 本文基于 Cognition SVP of Research Silas Alberti 接受 Anthropic 采访的官方文章整理。Cognition 是 Devin 的开发团队；文中关于模型表现、内部 benchmark 和未来判断，均为 Cognition / Anthropic 的公开说法，不等同于独立评测结论。

有一个画面，可能比“AI 又刷新了多少分”更能说明 Agent 正在发生什么变化：

工程师准备睡觉，把一个复杂的软件任务交给 Agent；第二天醒来，Agent 已经连续工作了八个小时，而且代码真的在向前推进。

这正是 Cognition 对 Claude Fable 5 的描述。

但这件事真正值得关注的地方，不是“AI 终于可以熬夜了”。

而是：一个 coding agent 要从“能完成几分钟的任务”，走到“可以在无人值守时段持续推进复杂工作”，中间需要跨过哪些能力门槛？

Anthropic 最近发布的一篇 Cognition 访谈，给出了一个很具体的答案。

## 01 过去的 Agent，最大问题是工作半径太短

Cognition 训练和测试了几乎每一代 Claude，并把模型放进 Devin 这个 AI software engineer 里验证。

他们发现，早期模型并不是完全不能工作，而是很难持续工作。

它们可能能坚持几分钟，复杂一点的任务也许能撑到一个小时。但上下文一长，任务一复杂，模型就容易失去主线：同时要权衡几件事时忘掉其中一件；迁移数据库时表面上完成了目标，却悄悄引入一串细小 bug；排查线上故障时停留在日志表面，找到第一个看似合理的原因就停止调查。

这类失败比“不会写代码”更麻烦。

因为它们往往会产生一个看起来像完成、实际上没有完成的结果。Agent 没有明确说“我卡住了”，而是自信地给出第一个 plausible answer，然后停下来。

对工程师来说，最危险的不是模型不会做，而是模型没有意识到自己还没有做完。

## 02 Fable 5 的变化，是把“任务 horizon”拉长

Cognition 自己做了一个叫 Frontier Code 的 benchmark。

他们之所以没有只看公开榜单，是因为一些现有评测会奖励“能通过测试的代码”，但这些代码未必能在真实代码库里长期维护。Alberti 把 Frontier Code 称为一种 “anti-slop” 标准：不只看结果对不对，也看实现是否足够接近工程师真正愿意留下来的代码。

在这个评测最难的子集上，之前的 Opus 模型得分大约是 10%，Claude Fable 5 达到约 30%。这个数字仍然谈不上“解决了软件工程”，但已经足以让 Cognition 的真实 dogfooding 与 benchmark 结果相互印证。

Alberti 认为，最明显的变化不是某一类题目的局部得分，而是模型的工作 horizon——它能够在多长时间内保持清醒、持续推进，而不丢失任务目标。

他提到，曾经有任务在自己睡觉前交给 Fable 5，让它继续工作；第二天醒来时，模型已经运行了八个小时，并且确实取得了进展。

这和“生成一段更长的代码”不是一回事。

更长的输出，只是 token 数量变多；更长的工作 horizon，意味着模型可以在多个动作之间保持目标、读取新信息、修正路线，并把前面的判断带到后面的执行里。

Agent 真正变强的标志，可能不是它一次能写多少行，而是它能不能在第 40 个动作之后，仍然记得第一个约束为什么重要。

## 03 可靠性来自“会调查”，不是来自“少犯错”

Cognition 观察到的另一个变化，是 Fable 5 开始更好地使用内部 debugging tools。

遇到复杂问题时，它不再只看最显眼的日志行，而是会在浏览器里翻查日志、定位噪声中的相关信息，再形成判断。

在一次让旧模型反复失败的迁移任务里，Fable 5 先明确自己要保持的 invariants，再围绕这些不变量执行。遇到 incident triage，它也更能追到 root cause，并说清楚哪些地方还不知道。

这里有一个很容易被忽略的变化：

“我不知道”不是 Agent 的失败状态，而是可信协作的一个组成部分。

如果 Agent 把第一个猜测当成结论，工程师就必须重新检查它的每一步；如果 Agent 能区分证据、推断和未知，工程师才可能把更多监督权交给它。

所以，Cognition 所说的“可以放着工作一夜”，并不只是模型更聪明。它还包括三件事：

1. 能在复杂上下文中保持主线。
2. 能主动使用工具获取证据，而不是只凭第一印象作答。
3. 能在证据不足时暴露不确定性，给人留下可审查的接力点。

这三件事共同构成了工程场景里的 trust。

## 04 “不相信任何评测”，其实是一套产品方法

Cognition 的工程师有一句很锋利的话：

> We trust no eval.

这并不是说 benchmark 没有价值，而是说 benchmark 不能代替真实工作。

他们会让高水平工程师把新模型放进一整天的真实任务里，最后判断：这段代码是不是自己愿意保留？这个迁移是否真的降低了风险？模型是否理解了代码库的约束？它是把问题解决了，还是把问题推到了下一层？

这套方法对所有 Agent 产品都适用。

评测可以回答“在某个定义好的任务上，模型表现如何”；真实工作还要回答：

- 它能不能处理脏上下文？
- 它会不会把错误假设带入后续步骤？
- 它能不能在工具返回噪声时继续调查？
- 它的改动是否符合团队的编码习惯？
- 它是否知道什么时候应该停下来找人？

最后几个问题，通常不会出现在一个漂亮的榜单里，却决定了 Agent 能不能进入生产环境。

## 05 从“写代码”到“管理一段持续运行的工作”

如果 Agent 只能完成几分钟的任务，人类仍然是执行者：自己拆需求，自己盯过程，自己决定每一步下一步做什么。

当 Agent 可以持续几个小时，人的角色就开始变化。

你不再只是在 prompt 里告诉它下一步怎么写，而是在任务开始时定义目标、约束、验证方式和交付标准；在任务结束时 review 它的结果、判断它是否真的达标。

这更接近项目管理，也更接近系统设计。

Cognition 的 founding bet，本来就是让 Agent 在云端持续运行数小时。随着 Fable 5 的能力提升，Devin 开始尝试更主动的工作方式：观察 Slack 频道，发现 issue 后主动介入；监控生产环境，在出现异常时自行开始 triage。

这提示了 coding agent 的下一种形态：

它不一定等你打开聊天框、输入一条命令。它可能持续观察某个工作环境，等到满足触发条件时，自己开始一段工作。

当然，“主动”不等于“自动批准一切”。越是长时间运行、越是能接触真实系统，权限边界、变更审批、回滚机制和证据记录就越重要。

真正成熟的 Agent，不是一个永远不打扰人的黑盒，而是一个能在低风险任务上自主推进、在高风险节点上准确请求确认的系统。

## 06 中文开发者可以提前准备什么

这篇访谈最值得借鉴的，不是“赶紧换成 Fable 5”，而是它暴露了一个事实：Agent 的能力上限，越来越取决于任务环境是否适合 Agent 工作。

如果希望未来的 coding agent 真正接手更长的任务，可以先从四件事开始准备。

### 第一，把验收标准写出来

“把这个功能做好”对人来说也许能靠经验理解，对 Agent 来说远远不够。

需要把什么算完成、哪些行为不能发生、要跑哪些测试、哪些文件不能碰，尽量变成明确的约束。

### 第二，让项目拥有可运行的反馈回路

Agent 需要通过命令、测试、日志和 diff 知道自己做得对不对。

没有可执行的验证路径，Agent 很容易停留在“看起来合理”。测试不一定能覆盖一切，但至少要让常见错误尽快暴露。

### 第三，把上下文放进工具，而不是只放在人的脑子里

代码库约定、架构决策、部署手册、故障排查路径，如果只存在于某几个资深工程师的记忆里，Agent 就很难持续工作。

好的 Agent 工作流，会把这些知识变成可检索、可执行、可验证的项目资产。

### 第四，设计“什么时候必须找人”

长任务不意味着完全无人监督。

更现实的设计是：低风险改动可以自主推进，涉及生产、权限、数据迁移或公共接口时必须暂停并请求确认。

这不是给 Agent 降级，而是在为它建立可以长期运行的信任边界。

## 结语：真正的突破，是 Agent 开始承担“过程”

过去我们评价 AI 编程工具，常问的是：它能不能写出这段代码？

接下来更重要的问题可能变成：它能不能在一个真实项目里，连续工作几个小时，持续验证自己的判断，并在不知道时停下来？

Cognition 对 Claude Fable 5 的评价，给出了一个值得记住的信号：Agent 的下一道门槛，不只是能力，而是持续性、可验证性和可托付性。

当模型开始承担一段工作的过程，而不只是生成某个瞬间的答案，软件工程的分工才真正开始改变。
