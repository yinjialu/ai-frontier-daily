# Claude Code 的模型和 effort 到底怎么选

> 本文基于 Anthropic 官方博客 [Choosing a Claude model and effort level in Claude Code](https://claude.com/blog/claude-model-and-effort-level-in-claude-code) 整理。原文作者 Lydia Hallie 是 Claude Code 团队成员。这里不是逐句翻译，而是把它改写成一篇面向普通 Claude Code 用户的使用指南。

Claude Code 里有两个很容易被混在一起的设置：

模型。

Effort level。

很多人会自然地把它们理解成同一种东西：模型越大越聪明，effort 越高就越认真。

这个理解有一半是对的。

模型越大，通常能力上限越高。它见过更多模式，能处理更复杂、更模糊、更陌生的问题。

但 effort 不只是“多想一会儿”。

Anthropic 这篇文章把这件事讲得很清楚：effort 控制的是 Claude Code 在这一轮任务里愿意做多少工作，包括读多少文件、用多少工具、验证到什么程度、在回来找你之前推进多少步骤。

所以更准确的说法是：

模型决定能力边界。

Effort 决定工作量预算。

这两个旋钮，一个像“你请的是谁”，一个像“你给他多少时间查资料、跑测试、反复确认”。

## 模型不是临时学习，而是换一组权重

先说模型。

Claude Code 在你按下回车时，会把你的消息、system prompt、工具定义、CLAUDE.md、对话历史、当前上下文里的文件，一起组装成一次 API 请求。

这些内容会进入模型，但不会改变模型本身。

原文里用了一个很基础也很重要的解释：模型真正“知道”的东西，存在它训练出来的 weights，也就是一大堆冻结的参数里。你给它 prompt，给它代码，给它文档，都是在 steering 它这一轮怎么预测下一个 token。

但你没有把知识写进 weights。

这也是为什么把某个新库文档贴给 Claude，它这一轮可以用，但这不叫“教会了模型”。下一轮如果没有这些文档，它仍然可能不知道。

所以，选择不同模型，本质上是在换一组冻结权重。

Sonnet、Opus、Fable 的差别，不是同一个人今天更努力或更懒，而是你换了不同能力上限的人。

这对使用 Claude Code 很关键。

如果一个问题需要的是底层能力，比如陌生架构判断、复杂 bug、模糊需求拆解、跨文件推理、领域知识迁移，那么换更强模型是合理的。

如果只是机械改名、补类型、按明确说明改几个文件，强模型可能不是必要条件。

不要把所有问题都归因于“模型不够聪明”。

有时候，模型知道怎么做，只是你没给它足够上下文。

有时候，模型知道，也有上下文，但它没有读够、查够、测够。

这就进入第二个旋钮：effort。

## Effort 不是聪明程度，而是愿意跑多远

Effort level 很容易被误解成“thinking time”。

但在 Claude Code 里，它影响的不只是思考文本长度。

Anthropic 原文明确说，它还会影响 Claude 读多少文件、使用多少工具、验证多少、在多步骤任务里推进多远再回来找你。

这点非常像真实工作。

你让一个工程师看一个 bug，他可以扫一眼就给判断，也可以花一下午读日志、跑测试、对比提交、验证假设。

同一个人，投入的调查深度不同，结果也会不同。

Effort 控制的就是这件事。

低 effort 时，Claude 更倾向于少消耗 token，遇到不确定就回来问你。它不一定会主动翻很多文件，也不一定会把测试跑到位。

高 effort 时，Claude 更愿意先自己推进：读更多上下文、列计划、调用工具、跑验证、检查替代假设，然后再回来。

所以当你觉得 Claude Code 没做好时，不要马上说“换大模型”。

先问一个更具体的问题：

它是“不知道”，还是“没试够”？

## 错了以后，先别调旋钮

这篇文章里最实用的一句话是：

Claude 做错时，第一反应不应该是调设置，而是检查你给的上下文。

这句话很重要，也很符合真实使用经验。

很多 Claude Code 失败，不是模型和 effort 的问题，而是上游问题：

任务描述太模糊；

仓库没有 CLAUDE.md；

没有告诉它哪里是测试入口；

没有给它必要的文档；

没有配置相关工具或 skill；

需求边界没有说清楚。

如果一个任务本来不该需要高 effort，却只能靠高 effort 才勉强做对，那很可能不是 effort 太低，而是上下文工程没做好。

比如你让它“修一下这个问题”，但没有告诉它错误日志、复现步骤、期望行为和测试命令。它当然可能乱翻一通。

更好的做法是先把任务喂清楚：

现象是什么；

哪里可以复现；

相关文件或模块在哪里；

什么结果算修好；

可以运行哪些测试；

哪些文件不要动。

这些东西比盲目拉高 effort 更有价值。

Effort 不是用来弥补混乱输入的万能药。

它更适合在上下文已经清楚时，决定 Claude 要不要更主动地查证和收尾。

## 一个最实用的判断表

我把原文的建议压缩成一个很实用的表。

如果 Claude 有上下文，也认真试了，但还是理解错、判断错、设计错，说明问题可能超出了当前模型能力边界。

这时换更强模型。

比如复杂架构决策、微妙 bug、陌生领域、模糊需求、多模块权衡，或者小模型反复给出看似合理但其实错的答案。

如果 Claude 做错，是因为跳过文件、没跑测试、没查调用链、重构半路停下、没有 double-check，那不是“不知道”，而是“没试够”。

这时提高 effort。

比如你已经给了测试命令，它却没跑；你要求改完整链路，它只改了入口；你让它确认兼容性，它只看了一处。

如果任务很机械，就用小模型或默认设置。

比如明确的文案修改、简单类型修复、局部重命名、格式调整、已经有上下文的问答。

如果任务很贵、很长、很模糊，先别急着拉满。把任务切小、写清验收标准，再决定模型和 effort。

很多时候，切任务比调旋钮更省钱。

## Sonnet、Opus、Fable：通才、专家和专科医生

Anthropic 原文里有一个很形象的比喻：

Sonnet 像很好的 generalist。

Opus 像 expert。

Fable 像 specialist。

Effort 决定的是他们在你这个任务上花多少时间。

这个比喻很适合普通用户理解。

Sonnet high effort，像给一个很好的通才一下午。他会认真读你的代码，跑工具，查上下文，最后对你的具体项目理解得很深。

Opus low effort，像找一个专家看五分钟。他有很多经验，可能一眼能看出方向，但不一定细读你仓库里的每个角落。

Fable low effort，像专科医生扫一眼疑难病例。它贵，能力上限高，适合那些其他模型怎么努力也够不到的问题。

这里没有绝对赢家。

模型是 capability。

Effort 是 thoroughness。

大多数真实任务都需要一点能力，也需要一点彻底。

关键是别把两者混为一谈。

## 成本不只是“模型单价”

很多人选模型时只看每 token 价格。

但 Claude Code 的成本还和完成任务需要多少步有关。

在简单任务上，大模型和小模型都能做对。大模型可能每 token 更贵，还可能做更多验证，这时用小模型更划算。

在复杂任务上，情况会反过来。

小模型可能绕很多圈，读很多文件，反复试错，最后仍然做不出来。大模型虽然每 token 贵，但可能更快到达正确路径，甚至总成本不一定更高。

更重要的是，有些任务不是“多给小模型一点 effort 就能解决”。

如果能力边界不够，再高 effort 也只是在边界附近打转。

这就是为什么 Fable 这种模型应该留给真正需要它的任务。

不是因为它总是更划算，而是因为它能解决一些其他模型够不到的问题。

## 我自己的使用建议

如果你只是普通使用 Claude Code，我会建议这样开始：

第一，默认 effort 先别动。

官方也建议大多数任务使用模型默认 effort，因为默认值本来就是在质量、速度和 token 消耗之间调过的平衡点。

第二，优先把上下文补好。

写清楚任务、约束、验收标准、测试命令。长期项目里维护好 CLAUDE.md，把常用命令、目录结构、代码规范、禁区都写进去。

第三，结果不对时先做诊断。

如果它没读文件、没跑测试、没查证，提高 effort。

如果它读了、试了、验证了，但结论仍然不行，换更强模型。

第四，把高 effort 用在“收尾”和“验证”上。

很多任务的主要实现不一定需要拉满，但最后让 Claude 做一次更高 effort 的 review、测试、边界检查，往往很值。

第五，把 Fable 留给硬骨头。

比如复杂迁移、架构判断、跨系统 debug、长链路重构、你自己也说不清哪里错但知道结果不对的任务。

## 这其实是 agent 的预算控制

我觉得这篇文章真正有价值的地方，不只是告诉你 Claude Code 两个设置怎么调。

它在解释一个更底层的东西：

Agent 产品的关键，不只是模型能力，而是预算控制。

一个 agent 每轮都在消耗资源：token、时间、工具调用、测试成本、人的注意力。

模型选择决定它的能力边界。

Effort 决定它愿意在这条路上走多远。

CLAUDE.md、skills、hooks、测试命令、任务拆分，则决定它有没有地图、工具和停止条件。

如果没有这些，调模型和 effort 只是瞎拧旋钮。

如果这些都设计好，Claude Code 就不再只是“一个会写代码的聊天框”，而更像一个可调度的工程代理。

你不是在追求每次都用最强模型、最高 effort。

你是在学会把不同任务放进不同预算里：

简单任务快速过；

重要任务认真查；

复杂任务请强模型；

长任务先拆小；

不确定任务先补上下文。

这才是 Claude Code 真正值得学的使用方式。

不是把旋钮全部拉满。

而是知道什么时候该拉，为什么该拉，拉了以后希望它多做哪一种工作。
