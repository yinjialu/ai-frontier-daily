# Claude Code 是怎么长出来的：从内部 CLI 到真正的编码 Agent

> 本文基于 Anthropic 官方文章 [The Making of Claude Code](https://www.anthropic.com/features/making-of-claude-code) 整理。原文是一篇口述史，采访对象包括 Anthropic 联合创始人、Claude Code 团队成员、研究员、产品设计师和早期用户。这里不是逐句全文翻译，而是尽量忠实保留原文信息、时间线和关键判断，并补充一点面向中文开发者的上下文。

如果你今天使用 Claude Code，很容易把它理解成一个“命令行里的 AI 编程工具”。

但 Anthropic 这篇口述史讲出来的不是一个工具的发布故事，而是一条更长的线：

从 2021 年研究团队训练 coding model，到 2022 年早期 VS Code 扩展和 agent harness；从内部命令行工具 clide，到 Boris Cherny 做出的 Claude CLI demo；再到 2025 年 Claude Code 对外发布，并随着 Claude 4 模型能力提升突然起飞。

这篇文章最值得看的地方，是它把一个今天看起来“理所当然”的产品形态还原成了很多不确定选择：

为什么是 CLI？

为什么 coding 会成为 Agent 最先突破的场景？

为什么一开始要忍受一个只能偶尔 work 的产品？

为什么小团队、快速反馈、真实用户，比一次性设计完美架构更重要？

下面按原文七个部分整理。

## 1. 起点：Anthropic 一开始就在想“自动化软件工程”

Claude Code 的源头比很多人想象得更早。

按 Anthropic 联合创始人 Ben Mann 的说法，公司很早决定要做产品时，第一个做出来的东西就是 coding assistant。那还是一个 VS Code extension：用户输入一个 prompt，它给出几个候选建议。

Shauna Kravec 负责强化学习方向。她提到，早在 2022 年，团队就在思考 coding assistant 和 autonomous software engineering。最初的训练任务很基础：模型能不能写一个简单函数？能不能写完后自己测试是否正确？

一开始效果很差。

但方向很明确：如果 AI 要走向更具变革性的能力，很可能要经过“大规模自动化软件工程”这一关。

这点对中文开发者很重要。

今天我们谈 Agent，容易把它看成一种产品形态：聊天窗口、工具调用、浏览器操作、任务队列。但在 Anthropic 的叙事里，Agent 不是从 UI 开始的，而是从训练和基础设施开始的。

要让模型真的写代码，不只是模型会生成文本。还需要运行环境、代码执行、测试反馈、安全隔离、超时处理、输入输出流、持久 shell。

Dawn Drain 在原文里提到，2022 年团队遇到的一个难题就是 harness design。所谓 harness，就是包在模型外面的脚手架：它让模型不只是“说”，而是真的能在一个环境里行动。

这也是 Claude Code 的底层主题。

Claude Code 从来不是“模型 + 聊天框”。它是模型、工具、shell、权限、上下文、文件系统、测试反馈和人类确认共同组成的系统。

## 2. 火花：clide 让团队第一次看到未来

到 2023 年，Anthropic 的研究团队开始做更开放的 Agent。模型可以做一些基本函数调用、搜索和工具使用。

在这个阶段，团队内部出现了一个叫 clide 的命令行工具。它可以让开发者在命令行里和 Claude 对话，用来编辑代码、处理开发任务。

原文里几个人对 clide 的描述很有意思：

它很慢，很笨拙，启动也不顺；但它让人第一次感觉到“未来已经露出来了”。

这是一类典型的早期产品状态：不是好软件，但它已经证明了某种新能力。

Dawn Drain 说，团队曾经让 clide 并行调用很多个 Claude Haiku，以回答一个完整文件夹的问题。Adam Wolff 也提到，他在 clide 里做过一个早期 agent 功能，能从局部改动推断用户想做什么。

这些听起来粗糙，但都指向后来的 Claude Code：

模型要能搜索代码库。

要能理解用户意图。

要能编辑文件。

要能运行命令。

要能在上下文不够时用工具补上下文。

真正的转折发生在 2024 年。

Ben Mann 成立 Labs 团队，看到 agentic coding 市场里有一个缺口。Boris Cherny 加入后，原本想先做一个更小的东西，比如 linter。但 Ben 的判断是：不要只咬一小口，要做“大的那个东西”。

Boris 后来做了一个两天 demo，叫 Claude CLI。

这个 demo 可以让 Claude 操作电脑上的东西，比如截图 Apple Music 并读出正在播放的音乐。Boris 自己说，当时没人太理解这个 demo，甚至他自己也不完全理解。但回头看，里面已经有今天 Claude Code 的原始元素。

这就是很多好产品早期的样子：

它不是从清晰 PRD 开始，而是从一个“好像有点魔法”的原型开始。

## 3. 团队：不是“AI 产品团队”，而是一群相信编程会变的人

原文第三部分讲团队背景。

这里最有意思的是，Claude Code 不是由一支传统意义上“开发者工具团队”从零规划出来的。

Adam Wolff 早年不是计算机科班，而是 film major，后来参与过 React。Igor Kofman 很小就开始写 BASIC。Fiona Fung 说，编程像一种讲故事和创造的方式。Cat Wu 最初是 Claude CLI 的重度内部用户，给 Boris 发大量反馈，后来加入团队。Meaghan Choi 则从设计角度看到：CLI 工具很少被认真设计，但这个东西只要一点设计投入，就可能成为真正的产品。

这段的价值不在个人履历，而在团队气质。

Claude Code 的早期团队不是先定义一个“AI IDE”大战略，而是围绕一个强烈的共同体感受聚集起来：

编程这件事正在变化。

CLI 不是过时界面，而可能是 Agent 最自然的入口。

如果模型能力继续上升，开发者和工具之间的关系会重写。

这也是为什么 Claude Code 没有一开始就做成一个重型 IDE 插件或 Web app。

它选择留在 terminal 里。对很多工程师来说，terminal 不是低级界面，而是最接近真实工作流的地方：git、测试、日志、部署、脚本、编辑器、包管理器都在那里。

Agent 如果要接管一部分软件工程，terminal 反而是最短路径。

## 4. 构建：小团队、真用户、极快反馈

原文第四部分最像产品复盘。

2024 年 10 月，Boris 几乎每周都在请求更多工程师。但 Adam Wolff 反而倾向于控制团队规模。

这听起来反直觉：这么重要的产品，为什么不快速扩张？

Anthropic 的回答是，小团队反而成了优势。

Boris 说，保持小团队让他们更有创造力，不容易过度工程化，也迫使团队更多使用 Claude，否则根本跑不快。

Sid Bidasaria 提到，最早很长一段时间，基本就是他、Boris 和 Ben 在做。到 2024 年 12 月拿到绿灯后，才有六七个人加入，进行了最后两周冲刺。今天很多核心功能，比如 bug reporting 和 login flow，就是那两周做出来的。

这段对做 AI 产品的人很有启发。

Claude Code 的早期迭代方式非常朴素：没有复杂 PR 限制，没有沉重 review 流程。用户说不喜欢什么，团队很快修，几分钟或几小时后就能通过 auto-update 送到用户手里。

它是 CLI 产品，所以没有复杂 Web 架构，也不用绕过太多发布链路。一个客户端应用，快速迭代，快速收集 metrics，快速响应用户。

但这里有一个更深的产品判断。

Ben Mann 提到，做模型产品化的人必须接受一种状态：你要先做一个今天只有 20% 或 30% 情况可用的东西。等下一个模型出来，它可能变成 80% 可用；再下一个模型出来，就可能接近真正的产品级。

这句话解释了很多 AI 产品的早期策略。

如果你等模型完全成熟再做产品，等你开始时，产品形态、用户习惯、反馈渠道、数据闭环都还没准备好。反过来，如果你太早做，就要忍受大量失败。

Claude Code 的做法是：先把产品壳、工具接口和反馈循环搭起来，等待模型能力跨过阈值。

## 5. 发布：从 Claude CLI 到 Claude Code

Claude Code 在 2025 年 2 月以 research preview 的形式对外发布。

原文说，早期访问阶段反响并不热烈。很多人觉得这个想法很酷，但 bug 太多。

发布时，Claude CLI 正式改名为 Claude Code。这个名字来自产品营销同事 Alex Isken 的提议，团队喜欢它的简单直接。

一些小细节也在这个阶段定型。

比如 terminal 里的 ASCII logo。Igor Kofman 说，他在发布前某个深夜觉得应该有一个 ASCII logo，于是和 Claude 一起填充字体，做出了后来标志性的 Claude Code 全大写 logo。

还有终端里的小角色 Clawd。Meaghan Choi 说，这类小小的 delight 很少能在产品里出现，但它让 Claude Code 不是冷冰冰的工具。

真正推动 Claude Code 扩散的，是早期用户。

Ramp 的 Austin Ray 是一个典型例子。他本来就是 terminal 用户，看到 Claude Code 能读文件、改文件、跑 bash 后，判断它会根本性改变软件开发。他开始在 Ramp 内部逐个拉人安装，让大家拿真实工作试。

Bun 创始人 Jarred Sumner 也提到，他让 Claude Code 根据 RFC 实现 websocket client compression。第一次做得不好，但经过多轮提示能自己修正。后来他甚至调整了 Bun 的优先级，让项目更适合和 Claude Code 协作。

这不是“AI 一次性写完代码”的故事。

更准确地说，是 Claude Code 让开发者开始改变工作流：

把任务拆给 Agent。

把项目整理得更容易被 Agent 理解。

把重复劳动转成自动化。

把反馈循环放进真实开发环境。

不过，原文也保留了反面经验。Anthropic 的 Tristan Hume 做性能工程，任务需要大量上下文，很多硬件细节还不公开。对他来说，早期 Claude Code 并不太有用，因为它还不会自己构建足够好的调查工具。

这点很真实。

Agentic coding 不是均匀降临在所有工程任务上的。越是上下文复杂、领域知识稀缺、工具链特殊的任务，越依赖模型是否能主动补齐环境和知识。

## 6. 新世界：从写 10% 代码到“管理一群 Claude”

原文第六部分讲 Claude Code 起飞后的变化。

Boris 说，2025 年 2 月时，Claude Code 也许只写了他 10% 的代码；到 5 月，比例变成 30% 到 40%；到 2025 年冬天，他已经不再手写任何一行代码。

这句话很容易被当成标题党，但它背后的重点不是“程序员不写代码了”，而是开发者角色开始上移。

Kyle Easterly 提到，开发者大致有两类：一类喜欢亲手写代码，把代码当成需要修剪的花园；另一类更在意真实用户是否用上了软件、是否喜欢它。他觉得自己属于后者。

Claude Code 对后者的意义更明显。

如果你的成就感来自“把东西做出来并被使用”，那么不亲手写每一行代码并不是损失，而是杠杆。

Shauna Kravec 则描述了另一种形态：她同时让一群 Claude 跑起来，读文档、更新内容、从 Slack 拉信息。Igor Kofman 顺着这个趋势说，下一层抽象可能不是你管理很多 Claude，而是你管理“Claude 的管理者”。

这其实就是今天很多人说的 multi-agent workspace。

第一阶段：人写代码，模型补全。

第二阶段：人描述任务，模型改代码。

第三阶段：人拆多个任务，多个 Agent 并行执行。

第四阶段：人不再直接管理每个 Agent，而是管理一个调度层、审查层或目标层。

Claude Code 正在把开发者推向后两层。

同时，用户对权限的态度也在变化。Cat Wu 说，最早大家会认真读每一个 permission request；后来很多用户开始 auto-accept。她把这看成 Claude 逐渐赢得信任的信号。

这也是 Agent 产品最核心的门槛：

不是能不能执行命令，而是用户敢不敢让它执行命令。

## 7. 未来：Claude Code 可能不会停留在 terminal

最后一部分是对未来的判断。

Adam Wolff 用 React 做类比。React 最初是一个很纯的计算机科学想法：用函数式方式表示 UI 状态。但当它拥有巨大用户规模后，它变成了 logo、品牌、感觉和社区，远不只是最初的技术洞见。

他认为 Claude Code 也会类似。

你今天以为 Claude Code 是 terminal、是某个提示技巧、是 Claude 的某种个性，但从长期看，这些都未必是本质。

Austin Ray 强调的是文化：在 Ramp 推动 Claude Code 时，他有意建立实验社区，公开讨论失败、有效经验和使用方式。他认为，复合式的群体知识非常关键。

Fiona Fung 则提醒，软件工程的角色会变化，而且变化速度快到很难预测下个月是什么样。团队需要持续向用户学习。

Tristan Hume 的判断更尖锐。他试着让 Claude 从零写一个 Jupyter Notebook 替代品，Claude 真的做出了可用东西。但他用起来并不喜欢，因为还缺少“taste”：知道他真正需要什么，并能在后台把它做好。

这也许是下一阶段 coding agent 的关键。

今天很多 Agent 已经能完成任务。

但“完成”不等于“有品味地完成”。

真正的高级软件工程，不只是把需求翻译成代码，还包括判断哪些需求不该做、哪些抽象会拖累系统、哪些界面让人不舒服、哪些实现未来会难维护。

模型要想从“能写代码”走向“能承担工程责任”，还需要跨过 taste、judgment 和 ownership 的门槛。

原文最后回到一个更长的历史视角：从打孔卡，到早期文本编辑器，再到今天的 Claude Code，编程工具一直在演化。Claude Code 只是这条光谱上的一个新点。

## 中文开发者应该从这篇文章里读到什么

如果把这篇文章只看作 Claude Code 宣传稿，会错过它最有价值的部分。

它其实给出了 Agent 产品的一套早期经验。

第一，coding 是 Agent 的关键试验场，不只是因为开发者愿意尝鲜，而是因为软件工程天然有可执行环境、测试反馈、版本控制和明确产物。这些东西让 Agent 能闭环。

第二，Agent 产品不能只看模型能力。Claude Code 的核心不是“Claude 会写代码”，而是 shell、文件系统、工具调用、权限、auto-update、metrics、用户反馈和团队迭代速度的组合。

第三，过早产品化不是坏事。只要你知道今天的能力只有 20% 或 30%，并且有耐心等模型进步，早期产品可以先建立用户、工作流和反馈循环。

第四，CLI 不是落后形态。对开发者来说，terminal 是真实工作发生的地方。Agent 要进入工程系统，最短路径可能不是漂亮 UI，而是能可靠地站在开发者已有工具链里。

第五，AI 编程的终点不是“替你打字”。更深的变化是开发者从写代码，变成组织任务、管理上下文、设计反馈回路、审查结果和塑造团队文化。

这也是我觉得这篇文章值得翻译和整理的原因。

它不是在说 Claude Code 已经完美。

它在说：软件工程正在进入一个新阶段。这个阶段里，代码不再只是人手写出来的文本，而是人、模型、工具、环境和组织流程共同产出的结果。

对中文开发者来说，真正的问题不是“要不要用 Claude Code”。

更现实的问题是：

你的项目、团队和工作流，准备好让 Agent 参与了吗？
